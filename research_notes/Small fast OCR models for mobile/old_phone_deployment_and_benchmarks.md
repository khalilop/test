## 1. Inference runtimes: for ncnn, MNN, LiteRT (ex-TensorFlow Lite), ONNX Runtime Mobile, Paddle Lite, ExecuTorch, Core ML and TNN, what are the minimum Android API / iOS version, ARMv7 support, library size and maintenance status in late 2026? Which are best for old CPUs without NEON dot-product/FP16?

### Takeaway
In November 2026 only **ncnn** (release 20261020) and **MNN** (3.6.2) are both actively released *and* still ship or document 32-bit ARMv7 Android builds with very low OS floors; LiteRT 2.3 raised its minSdk to 24, ExecuTorch's prebuilt AAR is 64-bit only (minSdk 23, iOS 17), Paddle Lite has published only release candidates since v2.12 (latest v2.14-rc, July 2024) and PaddleOCR's own mobile SDK has moved to ONNX Runtime (minSdk 26 / iOS 16), and TNN is dormant. On pre-ARMv8.2 cores (Cortex-A53/A72/A73: no dot-product, no FP16 arithmetic) measured INT8 speed-ups are only about 1.1-1.7x (sometimes negative) and FP16 gives nothing, so the runtime's plain ARMv7/ARMv8.0 NEON float kernels and threading matter more than quantization.

### Inferences
- For Android 5-6 or 32-bit-only devices the only *currently maintained* self-shipped options are ncnn and MNN (plus Tesseract4Android, see section 5). LiteRT >= 2.3 (API 24), ExecuTorch (arm64 only, API 23) and PaddleOCR's official ORT SDK (API 26) exclude them; older LiteRT 1.x / TFLite 2.x artefacts would still work but are in maintenance mode.
- "Best for old CPUs" on evidence: runtimes with hand-tuned ARMv7 and ARMv8.0 NEON float kernels and core-affinity controls (ncnn, MNN, Paddle Lite; XNNPACK inside LiteRT). Paddle Lite still has the most complete published ARMv7/Cortex-A53 numbers (section 3) but its maintenance state and missing 16 KB alignment make it a legacy choice; ncnn is the best-evidenced current choice (active, armv7 prebuilts, PP-OCRv5 demo at API 21).
- Since PaddleOCR itself now recommends ONNX Runtime for PP-OCRv6 on phones, the newest small models reach very old devices only via community conversions (ncnn/MNN), not via the vendor's SDK.

## 2. Platform changes that affect old-phone support (NNAPI deprecation, TFLite to LiteRT, Play 64-bit / target-API / 16 KB rules, ML Kit / Play services floors, Xcode deployment targets). What is the oldest Android/iOS version a newly published OCR app can realistically support in late 2026?

### Takeaway
Google Play policy constrains *target* API (36 for new apps/updates since 31 Aug 2026), 64-bit coverage and 16 KB alignment, not minSdk, so an app that ships its own native runtime can still declare minSdk 21 and include armeabi-v7a; what actually raises the floor is the dependency stack: Google Play services (and therefore unbundled ML Kit and Play-services LiteRT) now requires Android 7.0 / API 24 (July 2026), LiteRT 2.3 and Flutter require API 24, PaddleOCR's SDK and react-native-executorch require API 26. On iOS the toolchain is the limit: App Store uploads need the iOS 26 SDK (Xcode 26) whose deployment-target range reportedly starts at iOS 15, so iPhone 6s/7/SE-1 (stuck on iOS 15) are the oldest reachable devices and anything on iOS 12-14 is out.

### Cited Findings

#### Android / Google Play policy
- NNAPI "was introduced in Android 8.1 ... and deprecated in Android 15"; Google's migration advice is "TensorFlow Lite in Google Play Services and optionally TFLite GPU delegate for hardware acceleration". — [NNAPI Migration Guide](https://developer.android.com/ndk/guides/neuralnetworks/migration-guide)
- AOSP states the NNAPI NDK API is deprecated while the Neural Networks HAL interface continues to be supported. — [AOSP NNAPI runtime page](https://source.android.google.cn/docs/core/ota/modular-system/nnapi?hl=cs) [search summary]
- Target API: "Starting August 31 2026: New apps and app updates must target Android 16 (API level 36) or higher"; existing apps must target API 35+ to stay available to new users on newer OS versions; an extension to 1 November 2026 could be requested. The policy constrains `targetSdkVersion`, and the page says targeting a recent level means "your app can still run on older Android versions". — [Target API level requirements](https://developer.android.com/google/play/requirements/target-sdk)
- 64-bit: "for each native 32-bit architecture you support you must include the corresponding 64-bit architecture" (`armeabi-v7a` with `arm64-v8a`); "the 64-bit requirement does not apply to APKs or app bundles that are not distributed to devices running Android 9 Pie or later." Shipping 32-bit libraries alongside 64-bit ones remains allowed. — [Support 64-bit architectures](https://developer.android.com/google/play/requirements/64-bit)
- 16 KB pages: "all apps targeting Android 15 (API level 35) and higher must support 16 KB memory page sizes on 64-bit devices on Google Play. Starting February 1, 2027, if your app updates don't support 16 KB memory page sizes, you won't be able to release these updates." NDK r28+ aligns to 16 KB by default; AGP 8.5.1+ is needed for packaging; prebuilt `.so` files from SDKs must be recompiled; the alignment check script covers `arm64-v8a` and `x86_64` libraries. — [Support 16 KB page sizes](https://developer.android.com/16kb-page-size)

## 3. Measured numbers: what OCR latency and memory figures have been published for low-end or old devices (PP-OCR mobile, Tesseract, ML Kit, EasyOCR/docTR ports, custom CRNNs), plus general ARM tables for the relevant backbones?

### Takeaway
Published *OCR-specific* numbers on genuinely low-end phones are almost non-existent; the best public measurements are on 2019-2020 flagships: PaddleOCR's ONNX Runtime SDK reports about 420 ms for a 5-line image on a Snapdragon-855-class phone (detection about 83% of it), and react-native-executorch reports 425 ms (XNNPACK) for PP-OCRv6-small at 640x640 on a Galaxy S20+ with a 0.6-0.9 GB peak process footprint. For weak hardware one has to scale from backbone tables: a Cortex-A53 Snapdragon 625 is about 6-7x slower per thread than a Snapdragon 855 (MobileNetV3-large 96 ms vs 15.6 ms), and a Snapdragon 410 needs about 64 ms (4 threads) for one MobileNetV3 pass.

### Inferences
- "GM1900" is a OnePlus 7 model code (Snapdragon 855, 2019) by the researcher's recollection; the doc does not name the SoC. If right, a current official PaddleOCR pipeline costs about 0.42 s on a 2019 flagship for a 5-line image, with detection dominating (349 of 420 ms) and recognition costing about 12-13 ms per line.
- Scaling by Paddle Lite's single-thread ratios (Snapdragon 835 about 2.5-2.7x and Snapdragon 625 about 6.2-7.3x slower than Snapdragon 855 on MobileNetV3), the same pipeline at the same input size would land near 1.1 s on a Snapdragon-835-class phone and about 2.5-3 s on a Cortex-A53 phone (Snapdragon 625/450, Helio P22/A22, SC9863A class), before thermal effects. This is an extrapolation, not a measurement.
- The Snapdragon 410 block (4x A53 at 1.2 GHz) is the closest public proxy for Android-Go-class CPUs: about 64 ms for one MobileNetV3 224x224 pass with 4 threads. A DB-style detector at 640x640 covers about 8x the pixels of 224x224, so sub-second detection on such devices needs a much smaller input, a much smaller backbone (PP-OCRv6_tiny's 0.43M-parameter detector) or no detector at all.
- The S20+ row shows that even a 2020 flagship needs 0.36-0.53 s for PP-OCRv6-small at 640x640, and that peak process memory of 0.56-0.89 GB (React Native app included) is far beyond what 1-2 GB devices can spare; a native C++ pipeline should be much leaner but no public number was found.
- The Core ML rows (9.5 ms on an A15 iPhone SE vs 167 ms on XNNPACK) show how much the Neural Engine matters on A12+ devices and, by contrast, how exposed A9-A11 iPhones are (CPU/GPU only).

### Gaps
- No published OCR latency/memory was found for Snapdragon 4xx/6xx, Helio A/P/G, Unisoc or Exynos 7xxx phones, for Android Go devices, or for iPhone 6s/7/8 (A9-A11), for any engine (PP-OCR, Tesseract, ML Kit, EasyOCR, docTR).
- The PP-OCR paper's absolute Snapdragon 855 millisecond tables (arXiv blocked) and PaddleOCR GitHub issues with user-reported phone timings (search budget exhausted) were not retrieved. A search hit attributing "330 ms on CPU, 11.6M" to PP-OCRv2 could not be tied to a device.
- No absolute Tesseract-on-phone timing with `tessdata_fast` was found; the official Tesseract benchmark page lists only a desktop i7-10750H and its table was empty in the retrieved content ([tessdoc Benchmarks](https://tesseract-ocr.github.io/tessdoc/Benchmarks.html) [search summary]).
- No on-device numbers for EasyOCR or docTR ports were retrieved (Qualcomm AI Hub's `perf.yaml` path returned 404). AI Benchmark's OCR sub-test results per SoC were not found.
- Search surfaced, but I could not open or attribute, a desktop/server comparison ("Tesseract 453 ms, EasyOCR 715 ms, PaddleOCR 2,143 ms") and a paper statement that PaddleOCR's 4.5 GB peak memory makes it impractical on-device; both describe Python/server pipelines and should not be used for phones. ## 4. Optimization techniques and their measured effect (INT8 PTQ vs QAT, FP16, pruning/distillation, detection input size, ROI / skipping detection, batching, threads and big.LITTLE, XNNPACK, GPU delegates on old GPUs, memory mapping, warm-up/load time, thermal throttling)

### Takeaway
On old CPUs the largest, best-evidenced wins are structural: shrink the detector input and skip detection when the text region is known (detection was 83% of pipeline time in PaddleOCR's own phone sample), then use 2-4 threads on the right cores; INT8 is worth about 1.2-1.7x on Cortex-A53/A73-class cores (versus 1.6-2.5x on dot-product cores) and can hurt recognition accuracy, FP16 only helps on ARMv8.2+, and GPU backends are frequently slower than the CPU for small models and cannot run quantized or dynamic-shape models in some runtimes.

### Cited Findings

#### INT8: post-training quantization vs quantization-aware training
- Paddle Lite v2.11, 1 thread, FP32 to INT8: Snapdragon 625 armv8 MobileNetV3_large 96.11 to 66.76 ms and MobileNetV3_small 39.08 to 22.83 ms; armv7 102.01 to 76.98 and 37.74 to 26.86; Snapdragon 835 armv8 MobileNetV3_large 41.74 to 30.57; Snapdragon 855 armv8 MobileNetV1 29.04 to 11.86 and MobileNetV3_large 15.59 to 8.88. — [Paddle-Lite benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/performance/benchmark.md)
- PaddleSlim model zoo: QAT and PTQ models have identical latency; on Snapdragon 835 (armv8, 1 thread) MobileNetV1 88.50 ms FP32 vs 56.43 (QAT) / 56.53 (PTQ); MobileNetV2 61.36 vs 46.15 / 45.87; on Kirin 970 94.90 vs 57.75; on Snapdragon 855 armv8 31.35 vs 14.02 but on Snapdragon 855 **armv7** 33.51 vs 36.71 (INT8 slower). Accuracy: MobileNetV1 top-1 70.99% FP32, 70.18% PTQ, 70.60% QAT; MobileNetV2 72.15% / 71.15% / 72.05%. Size: 17 MB to 4.4 MB and 15 MB to 4.0 MB. — [PaddleSlim model_zoo](https://raw.githubusercontent.com/PaddlePaddle/PaddleSlim/develop/docs/zh_cn/model_zoo.md)
- TFLite on Pixel 2 (single big core): Mobilenet-v1 124 ms float, 112 ms post-training quantized, 64 ms quantization-aware; Mobilenet-v2 89 / 98 / 54 ms (PTQ was slower than float); top-1 0.709 / 0.657 / 0.70 and 0.719 / 0.637 / 0.709; size 16.9 to 4.3 MB and 14 to 3.6 MB. — [TF r2.15 model_optimization.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/performance/model_optimization.md)
- TFLite's nominal claims: dynamic-range quantization "4x smaller, 2x-3x speedup"; full-integer "4x smaller, 3x+ speedup"; float16 "2x smaller, GPU acceleration" and a float16 model is dequantized to float32 on CPU. — [TF r2.15 post_training_quantization.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/performance/post_training_quantization.md)
- ncnn's own benchmark shows INT8 is not reliably faster on old cores: `mobilenet_int8` vs `mobilenet` at 4 threads = 64.13 vs 90.03 ms on Snapdragon 410 and 20.46 vs 27.88 on Snapdragon 821 (faster), but 64.49 vs 37.32 on Snapdragon 835, 55.38 vs 35.93 on Kirin 970 and 82.98 vs 32.33 on Snapdragon 660 (slower); on the A7 iPhone 5S 111.38 vs 79.44 (slower). — [ncnn benchmark README](https://raw.githubusercontent.com/Tencent/ncnn/master/benchmark/README.md)
- MNN's rule of thumb: INT8 on ARMv7a/ARMv8 without sdot is about 30% faster than float; with unsupported ops falling back to float it can be slower. — [MNN faq.md](https://raw.githubusercontent.com/alibaba/MNN/master/docs/faq.md)
- A peer-reviewed mobile study found quantized models' runtime advantage "was not dramatic in the majority of cases, lying below 25-30%", and some chipsets (Kirin 990/980, Snapdragon 888) could not run quantized TFLite models on accelerators. — [arXiv 2105.07869](https://arxiv.org/pdf/2105.07869) [search summary]
- OCR-specific accuracy effect (PaddleSlim auto-compression, QAT + distillation): PP-OCRv3 detection Hmean 84.57 to 85.01, PP-OCRv3 recognition accuracy 76.48 to 73.23 (latency columns empty). — [PaddleSlim ACT OCR example](https://raw.githubusercontent.com/PaddlePaddle/PaddleSlim/develop/example/auto_compression/ocr/README.md)
- react-native-executorch ships its PP-OCRv6 pipeline with an int8 DBNet detector but an fp32 SVTR recognizer because int8 "degrades accuracy on the SVTR attention stack"; that mixed model is 23 MB vs 30 MB all-fp32 and runs 425 vs 535 ms on a Galaxy S20+ and 167 vs 198 ms on an iPhone SE 3. — [RN ExecuTorch benchmarks page](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/docs/docs/04-benchmarks/01-benchmarks.mdx); [imported.json](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/docs/docs/04-benchmarks/imported.json)
- PaddleOCR's quantized "slim" Paddle-Lite bundles: PP-OCRv3 16.2M to 5.9M (slim); PP-OCRv2 11M to 4.6M (slim); the demo is run with precision "INT8" for quantized models or "FP32" otherwise. — [PaddleOCR deploy/lite readme](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/release/2.7/deploy/lite/readme.md)
- PaddleOCR's quantization doc warns that a quantization-trained model exported normally still has float32 parameters and gives no speed-up unless the runtime executes INT8. — [PaddleOCR quantization doc](https://www.paddleocr.ai/v2.10.0/ppocr/model_compress/quantization.html) [search summary]
- ncnn post-training INT8 workflow: `ncnnoptimize`, `ncnn2table` (kl, aciq, eq, percentile calibration; more than 5,000 calibration images recommended), `ncnn2int8`; individual layers can be kept float32 by commenting out their scale line; no speed claim is made. — [ncnn quantized-int8-inference.md](https://raw.githubusercontent.com/Tencent/ncnn/master/docs/how-to-use-and-FAQ/quantized-int8-inference.md)

#### FP16
- FP16 arithmetic on CPU needs ARMv8.2: Paddle Lite FP16 results (Snapdragon 845: MobileNetV1 58.70 to 29.62 ms; MobileNetV3_large 29.55 to 15.77 ms) exist only for Snapdragon 865/855/845 and Kirin 990. — [Paddle-Lite benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/performance/benchmark.md)
- MNN: "Twice speed increase for the new architecture ARM v8.2 with FP16"; FP16 weights alone do not speed up inference. — [MNN README](https://raw.githubusercontent.com/alibaba/MNN/master/README.md); [MNN faq.md](https://raw.githubusercontent.com/alibaba/MNN/master/docs/faq.md)
- On GPU, FP16 is the default: Paddle Lite OpenCL uses fp16 on Android by default (`CL_PRECISION_AUTO`); MNN OpenCL `Precision_Low` = fp16 storage and compute. — [Paddle-Lite opencl.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/demo_guides/opencl.md); [MNN session.md](https://raw.githubusercontent.com/alibaba/MNN/master/docs/inference/session.md)

#### Pruning and distillation
- PaddleSlim on Snapdragon 845 (armv8, Paddle Lite v2.3; 1 / 2 / 4 threads): MobileNetV1 baseline 66.05 / 35.80 / 19.58 ms; uniform -50% FLOPs 33.56 / 18.68 / 10.51 ms with top-1 -1.59%; sensitivity-based -30% 46.60 / 25.31 / 13.70 ms with -0.59%; MobileNetV2 uniform -50% 41.79 to 23.88 ms at 1 thread but top-1 -6.35%. — [PaddleSlim model_zoo](https://raw.githubusercontent.com/PaddlePaddle/PaddleSlim/develop/docs/zh_cn/model_zoo.md)
- PP-OCR's detector with FPGM pruning: size -46.2%, time -18.9% on Snapdragon 855, HMean slightly lower. — [PP-OCR, arXiv 2009.09941](https://arxiv.org/pdf/2009.09941) [search summary]
- TFLite caveat: "Pruned models are the same size on disk, and have the same runtime latency, but can be compressed more effectively" (unstructured sparsity does not speed up TFLite). — [TF r2.15 model_optimization.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/performance/model_optimization.md)
- PP-OCRv6_tiny has no neck and is trained with knowledge distillation from the medium model. — [PaddleOCR PP-OCRv6 doc](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.en.md)

#### Detection input resolution, region of interest, skipping stages
- Paddle-Lite mobile config defaults: `max_side_len 960`, `det_db_thresh 0.3`, `det_db_box_thresh 0.5`, `det_db_unclip_ratio 1.6`, `use_direction_classify 0`, `rec_image_height 48` (PP-OCRv3) or 32 (PP-OCRv2). — [PaddleOCR deploy/lite readme](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/release/2.7/deploy/lite/readme.md)
- PaddleOCR's 2026 Android SDK defaults: `detLimitSideLen: 64`, `detLimitType: "min"`, `detMaxSideLimit: 4000`, `recBatchSize: 1`; the only thread value shown is `EngineConfig(numThreads = 4)`. — [PaddleOCR android_deployment.en.md](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/inference_deployment/cross_platform/android_deployment.en.md)
- `limit_type` "min" keeps the shortest side at or above the limit, "max" keeps the longest side at or below it; the FAQ suggests `limit_type=min, limit_side_len=960` for lower-resolution images and larger values such as 1216 when more detection scale is needed. — [PaddleOCR text_detection module](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/module_usage/text_detection.en.md)
- The ncnn PP-OCRv5 phone demo converts detectors at 320x320 and 256x256 and recognizers at 48x160 and 48x256 (dynamic shapes enabled manually). — [nihui/ncnn-android-ppocrv5](https://github.com/nihui/ncnn-android-ppocrv5)
- react-native-executorch benchmarks OCR at a 640x640 frame; PP-OCRv6's paper quotes CPU latency at 2048 resolution. — [RN ExecuTorch benchmarks page](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/docs/docs/04-benchmarks/01-benchmarks.mdx); [PP-OCRv6, arXiv 2606.13108](https://arxiv.org/pdf/2606.13108) [search summary]
- Stage skipping is a first-class option in PaddleOCR's Paddle-Lite Android demo: six run modes (det+cls+rec default, det+rec, cls+rec, det only, rec only, cls only), plus settings for CPU thread number, CPU power mode, detector long-side size and score threshold. — [PaddleOCR android_demo README](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/release/2.7/deploy/android_demo/README.md)
- In PaddleOCR's phone sample, detection is 348.70 ms of 420.40 ms and recognition 66.20 ms for 5 lines. — [PaddleOCR android_deployment.en.md](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/inference_deployment/cross_platform/android_deployment.en.md)

#### Threads, big.LITTLE affinity
- ncnn: reduce threads to "half of the cpu cores count or less"; `set_cpu_powersave(2)` binds to big cores, `1` to little cores, `0` all cores; OpenMP busy-wait ("the thread need to busy-wait up to 200ms") costs CPU and can be shortened with `set_kmp_blocktime` / `opt.openmp_blocktime`; with one core or Vulkan, disable OpenMP. — [ncnn openmp-best-practice.md](https://raw.githubusercontent.com/Tencent/ncnn/master/docs/how-to-use-and-FAQ/openmp-best-practice.md); [ncnn faq.md](https://raw.githubusercontent.com/Tencent/ncnn/master/docs/faq.md)
- Paddle Lite power modes: `LITE_POWER_HIGH` binds big cores and scales the thread count down to the number of big cores (it falls back to no binding if binding fails, which the doc says can happen on some phones in low-battery conditions); `LITE_POWER_LOW` binds little cores; `LITE_POWER_FULL` uses both; `LITE_POWER_NO_BIND` is the recommended mode; default is one thread and threads only take effect with OpenMP. — [Paddle-Lite cxx_api_doc.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/api_reference/cxx_api_doc.md)
- Measured scaling: Snapdragon 835 mobilenet_v1 87.46 / 48.02 / 26.42 ms at 1 / 2 / 4 threads (Paddle Lite v2.6); Snapdragon 410 mobilenet_v3 147.55 ms (1 thread) vs 63.90 ms (4 threads) (ncnn); Snapdragon 810 mobilenet_v2 33.56 ms on all 8 cores vs 43.62 ms on the 4 big cores (ncnn). — [Paddle-Lite v2.6 benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/release/v2.6/docs/benchmark/benchmark.md); [ncnn benchmark README](https://raw.githubusercontent.com/Tencent/ncnn/master/benchmark/README.md)
- TFLite guidance: multi-threading "comes at the cost of increased performance variability"; isolated tests may show 2x but a competing app can make it slower than single-threaded; more threads cost power. Java `ByteBuffer` inputs are much faster. — [TF r2.15 best_practices.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/performance/best_practices.md)
- MNN: `numThread` plus `BackendConfig` power/precision/memory preferences; explicit core binding via `Interpreter::setSessionHint(HintMode::CPU_CORE_IDS)` before `createSession`. — [MNN session.md](https://raw.githubusercontent.com/alibaba/MNN/master/docs/inference/session.md)

#### GPU backends on old GPUs
- ncnn Vulkan vs CPU (same blocks as above, avg ms): iPhone 5S GPU squeezenet 261.09 vs CPU 2-thread 49.74; Snapdragon 810 GPU mobilenet_v3 46.69 vs CPU 4-thread 37.65 (squeezenet 40.62 vs 43.08); Kirin 970 GPU mobilenet_v3 35.51 and shufflenet_v2 31.27 vs CPU 4-thread 23.07 and 15.37; Snapdragon 765G GPU mobilenet_v2 32.40 vs CPU 4-thread 13.27; Snapdragon 855+ GPU squeezenet 9.09 vs CPU 4-thread 3.64. — [ncnn benchmark README](https://raw.githubusercontent.com/Tencent/ncnn/master/benchmark/README.md)
- Paddle Lite OpenCL (auto-tune on) vs 1 CPU thread: Snapdragon 625 / Adreno 506 MobileNetV1 56.04 ms (CPU 143.64), MobileNetV3_large 40.58 (CPU 96.11), MobileNetV3_small 19.12 (CPU 39.08); Snapdragon 835 / Adreno 540 MobileNetV1 10.13 (CPU 82.48), MobileNetV3_small 10.37 (CPU 13.45); Snapdragon 855 / Adreno 640 MobileNetV3_small 6.79 (CPU 5.39, GPU slower). — [Paddle-Lite benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/performance/benchmark.md)
- Paddle Lite OpenCL limits: "模型推理速度并不一定会比在 CPU 上执行快" (not necessarily faster than CPU); ops without a GPU kernel fall back to CPU; quantized models are not supported; dynamic-shape models may throw errors; the first run has initialization overhead mitigated by `set_opencl_binary_path_name` (kernel-binary cache) and `set_opencl_tune`. — [Paddle-Lite opencl.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/demo_guides/opencl.md)
- TFLite GPU delegate: quantized models are executed as float; a CPU/GPU split "often results in slower performance than when the whole network is run on" the CPU; serialization of compiled kernels "can reduce startup time by up to 90%"; for "a very small model, it may not be worth delegating". — [TF r2.15 gpu.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/performance/gpu.md); [TF r2.15 best_practices.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/performance/best_practices.md)
- MNN: GPU can be slower because some mobile GPUs are weak, memory bandwidth limits them, the system throttles GPU frequency or CPU fallbacks add copies; heavier GPU tuning modes lengthen first initialization; `setCacheFile` speeds later initializations. — [MNN faq.md](https://raw.githubusercontent.com/alibaba/MNN/master/docs/faq.md); [MNN session.md](https://raw.githubusercontent.com/alibaba/MNN/master/docs/inference/session.md)
- OCR on GPU in 2026 data: Vulkan vs XNNPACK for PP-OCRv6-small is 360 vs 425 ms on a Galaxy S20+ but 39 vs 188 ms on a Galaxy S26 Ultra. — [RN ExecuTorch imported.json](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/docs/docs/04-benchmarks/imported.json)
- ncnn FAQ: GPUs drop into power-saving after idle; one log shows about 190 ms per frame after a 3-second pause vs about 40 ms before. — [ncnn faq.md](https://raw.githubusercontent.com/Tencent/ncnn/master/docs/faq.md)

#### Model load, memory mapping, warm-up, thermal
- Cold load measurements: PaddleOCR Android SDK 158 ms (Snapdragon-855-class); PP-OCRv6-small on ExecuTorch 67-116 ms on a Galaxy S20+, 137-264 ms on a Pixel 10, 30-38 ms (XNNPACK) vs 159 ms (Core ML) on an iPhone SE 3. — [PaddleOCR android_deployment.en.md](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/inference_deployment/cross_platform/android_deployment.en.md); [RN ExecuTorch imported.json](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/docs/docs/04-benchmarks/imported.json)
- ncnn offers "Direct memory reference loading for `.param` and `.bin` models" and added mmap model loading plus a persistent Vulkan pipeline cache in 20260526. — [ncnn README](https://raw.githubusercontent.com/Tencent/ncnn/master/README.md); [ncnn releases](https://github.com/Tencent/ncnn/releases)
- MNN: `createSession` is expensive, so create once and reuse; `resizeSession` only when input dimensions change; `releaseModel` frees model data after sessions exist. — [MNN session.md](https://raw.githubusercontent.com/alibaba/MNN/master/docs/inference/session.md)
- Warm-up conventions: PaddleOCR's phone benchmark discards 3 warm-up runs before 10 measured runs. — [PaddleOCR android_deployment.en.md](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/inference_deployment/cross_platform/android_deployment.en.md)
- Thermal: Android's Thermal API (`getThermalHeadroom`, Java API from Android 11 / API 30, NDK API from Android 12 / API 31) predicts throttling; it must not be polled more than once every 10 seconds and returns NaN on unsupported devices; the recommended response is to cut worker threads, change core affinity or lower frame rate before throttling. — [Android Thermal API](https://developer.android.com/games/optimize/adpf/thermal)
- Benchmarks are explicit about thermal variance: react-native-executorch notes that run-to-run variation is common because of background tasks and thermal management; ncnn's benchmark has a `cooling_down` parameter. — [RN ExecuTorch benchmarks page](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/docs/docs/04-benchmarks/01-benchmarks.mdx); [ncnn benchmark README](https://raw.githubusercontent.com/Tencent/ncnn/master/benchmark/README.md)
- A caution on tool numbers: LiteRT benchmark-tool times are kernel-only and exclude preprocessing, memory overhead and scheduling. — [arXiv 2604.17007](https://arxiv.org/pdf/2604.17007) [search summary]

### Inferences
- Computed INT8 speed-ups from the cited tables: Snapdragon 625 (A53) 1.2-1.7x on arm64 and 1.1-1.4x on armv7; Snapdragon 835 / Kirin 970 (A73) 1.2-1.6x; Snapdragon 855 (A76, dot-product) 1.6-2.5x. So on the target devices quantization is mainly a *size* optimization (about 4x smaller) with a modest speed bonus, and should be applied to the detector first because recognizers lose accuracy (PP-OCRv3 rec -3.25 points; ExecuTorch keeps SVTR in fp32).
- Runtime version matters as much as the technique: armv7 INT8 on Snapdragon 855 was slower than FP32 in Paddle Lite v2.6 (37.18 vs 35.11 ms) but 2x faster in v2.11 (16.11 vs 33.44 ms); ncnn's old blocks show INT8 regressions that newer versions may have fixed. Always benchmark the exact runtime build on a target device.
- A 32-bit (armeabi-v7a) build costs 0-25% versus arm64 on the same chip (Snapdragon 625 MobileNetV2 131.05 vs 106.17 ms; MobileNetV3_small 37.74 vs 39.08 ms), so shipping arm64 wherever the OS is 64-bit is a free gain, but many low-end devices with 64-bit SoCs run 32-bit Android (not quantified here).
- Convolution cost is roughly proportional to pixel count, so capping the detector's long side at 640 instead of 960 is about 2.25x less detector work and 480 is about 4x less. PaddleOCR's current Android SDK default (`detLimitType "min"`, 64 px, with a 4000 px maximum) effectively does not downscale camera frames, so on an old phone the app must impose its own cap.
- With a fixed capture guide (ID/MRZ line, meter reading, serial number) the detector and direction classifier can be dropped: on the Snapdragon-855 sample that would cut 420 ms to roughly the 66 ms recognition share (about 13 ms per line), i.e. roughly 80-100 ms per line on a Cortex-A53 phone by the 6-7x scaling. This is an extrapolation.
- For OCR, GPU backends are risky on old phones: recognition inputs are variable-width (dynamic shape), quantized models are unsupported or run as float on GPU, 11% of handhelds have no or only Vulkan 1.0, and measured small-model GPU results on Adreno 430/620, Mali-G72 and PowerVR are at or below 4-thread CPU speed. OpenCL on Adreno (Paddle Lite: 2-2.6x over one A53 thread on Snapdragon 625) is the one old-GPU case with positive evidence, but it compares against a single CPU thread.
- Thread advice consistent with all sources: 2-4 threads; on big.LITTLE bind to big cores, on homogeneous 8x A53 SoCs use about 4; for continuous camera OCR drop to fewer threads or lower frame rate when thermal headroom falls.

### Gaps
- No measurement of recognition batching on phones was found (PaddleOCR's SDK defaults to `recBatchSize: 1`; ncnn only added native batch inference in October 2026).
- No OCR-specific measurement of thermal throttling during continuous camera scanning, and no measured effect of mmap vs copy loading on low-RAM phones.
- No published QAT-vs-PTQ comparison specifically for OCR recognizers on ARM latency; PaddleSlim's OCR table has empty latency columns.
- TFLite documents cited are from TF 2.15 (2023); LiteRT 2.x's current docs (ai.google.dev / developers.google.com) could not be opened, so GPU-delegate and Play-services details may have changed.

## 5. App size and delivery: how small can a full on-device OCR feature be (runtime + models) with each approach; on-demand delivery; system OCR vs shipping your own models

### Takeaway
The smallest footprint is system or unbundled OCR (Apple Vision: zero bytes; ML Kit via Play services: about 260 KB per script), followed by self-shipped stacks of roughly 5-10 MB built from a sub-megabyte runtime plus a tiny model set (PP-OCRv6_tiny 6.3 MB, PP-OCRv2/v3 slim 4.6-5.9 MB, Tesseract fast English 3.9 MB); typical "comfortable" stacks (ONNX Runtime plus PP-OCRv5 mobile or PP-OCRv6 small) are 20-35 MB of models before the runtime. Google Play can deliver models after install (asset packs / AI packs, with device targeting by RAM or SoC) but AI packs cannot contain native libraries.

### Cited Findings

#### Sizes
- ML Kit Text Recognition v2 on Android: unbundled (Play services) and bundled install paths; the documented app-size impact is about 260 KB per script per architecture and about 4 MB per script per architecture (the snippet did not label which is which; by the researcher's recollection of the page the 260 KB figure is the unbundled library and 4 MB the bundled one). Unbundled models "do not add to app size"; bundled gives immediate offline use. — [ML Kit text recognition v2 (Android)](https://developers.google.com/ml-kit/vision/text-recognition/v2/android) [search summary]; [ML Kit installation paths](https://developers.google.com/ml-kit/tips/installation-paths) [search summary]
- Tesseract English data: `tessdata_fast` 3.92 MB; `tessdata_best` 14.7 MB; `tessdata` (legacy + LSTM) 22.4 MB. — [tessdata_fast eng](https://github.com/tesseract-ocr/tessdata_fast/blob/main/eng.traineddata); [tessdata_best eng](https://github.com/tesseract-ocr/tessdata_best/blob/main/eng.traineddata); [tessdata eng](https://github.com/tesseract-ocr/tessdata/blob/main/eng.traineddata)
- Tesseract's own guidance: `tessdata_fast` uses integer LSTM models from a smaller network and is the best "value for money"; "Most users will want tessdata_fast"; `tessdata_best` is "for people willing to trade a lot of speed for slightly better accuracy"; only `tessdata` supports the legacy recognizer. — [tessdoc Data-Files](https://raw.githubusercontent.com/tesseract-ocr/tessdoc/main/Data-Files.md)
- Tesseract4Android: Tesseract 5.5.1 + Leptonica 1.85.0; latest release 4.9.0 ("11 Jun", 2025 inferred), 4.8.0 ("01 Dec", 2024 inferred) raised minSdk to 21 and added 16 KB support; two variants, Standard (single-threaded) and OpenMP (multi-threaded); trained data must live in a `tessdata` directory in app-private storage when targeting API 29+. — [Tesseract4Android README](https://raw.githubusercontent.com/adaptech-cz/Tesseract4Android/master/README.md); [Tesseract4Android releases](https://github.com/adaptech-cz/Tesseract4Android/releases)
- PaddleOCR model storage sizes: PP-OCRv6_tiny_det 1.9 MB + PP-OCRv6_tiny_rec 4.4 MB; PP-OCRv6_small_det 9.6 MB + PP-OCRv6_small_rec 20.4 MB; PP-OCRv5_mobile_det 4.7 MB + PP-OCRv5_mobile_rec 16 MB; PP-OCRv4_mobile_det 4.7 MB + PP-OCRv4_mobile_rec 10.5 MB; PP-OCRv3_mobile_rec 10.3 MB; en_PP-OCRv5_mobile_rec 7.5 MB; latin_PP-OCRv5_mobile_rec 14 MB. — [PaddleOCR text_detection module](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/module_usage/text_detection.en.md); [text_recognition module](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/module_usage/text_recognition.en.md)
- Paddle-Lite `.nb` bundles (det + cls + rec): PP-OCRv3 16.2M, PP-OCRv3 slim 5.9M, PP-OCRv2 11M, PP-OCRv2 slim 4.6M. — [PaddleOCR deploy/lite readme](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/release/2.7/deploy/lite/readme.md)
- Original PP-OCR slim system: 3.5M (Chinese, 6,622 characters) and 2.8M (63 alphanumeric symbols). — [PP-OCR, arXiv 2009.09941](https://arxiv.org/pdf/2009.09941) [search summary]
- ExecuTorch-packaged PP-OCRv6-small: 23 MB (int8 detector + fp32 recognizer), 30 MB fp32, 25 MB Vulkan, 8 MB Core ML (as listed in the benchmark data). — [RN ExecuTorch imported.json](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/docs/docs/04-benchmarks/imported.json)
- Runtime library signals: MNN core `.so` about 800 KB (armv7a); TNN about 400 KB; TFLite selective build about 0.30 MB (armeabi-v7a) / 0.38 MB (arm64-v8a) for a MobileNet op set; ORT 1.11-era Android package 3.3 MB (mobile) / 12 MB (full); Paddle-Lite prebuilt archives 3.6-4.5 MB (11.2-11.5 MB `with_extra`). — [MNN README](https://raw.githubusercontent.com/alibaba/MNN/master/README.md); [Tencent/TNN](https://github.com/Tencent/TNN); [TF r2.15 reduce_binary_size.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/guide/reduce_binary_size.md); [onnxruntime.ai mobile tutorial](https://onnxruntime.ai/docs/tutorials/mobile) [search summary]; [Paddle-Lite releases](https://github.com/PaddlePaddle/Paddle-Lite/releases)
- Dependencies add weight beyond the inference runtime: PaddleOCR's Android SDK needs OpenCV 4.5.3 and coroutines in addition to ONNX Runtime ("The AAR does not pull in dependencies"); older community apps pin OpenCV 3.4.15 to keep minSdk 21. — [PaddleOCR android_deployment.en.md](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/inference_deployment/cross_platform/android_deployment.en.md); [benjaminwan/OcrLiteAndroidNcnn README](https://raw.githubusercontent.com/benjaminwan/OcrLiteAndroidNcnn/master/README.md)
- Quantization as a size lever: about 4x smaller for INT8 (MobileNetV1 17 MB to 4.4 MB), 2x for float16. — [PaddleSlim model_zoo](https://raw.githubusercontent.com/PaddlePaddle/PaddleSlim/develop/docs/zh_cn/model_zoo.md); [TF r2.15 post_training_quantization.md](https://raw.githubusercontent.com/tensorflow/tensorflow/r2.15/tensorflow/lite/g3doc/performance/post_training_quantization.md)

#### Delivery mechanisms (Android)
- Play Asset Delivery modes: `install-time` packs "contribute to the app size listed on the Google Play Store"; `fast-follow` packs download automatically right after install and `on-demand` packs download at runtime, and neither contributes to the listed size. Storage: install-time packs "require at least two times the size of all the asset packs", fast-follow/on-demand "only a few hundred extra MBs". — [Play Asset Delivery](https://developer.android.com/guide/playcore/asset-delivery)
- Play for On-device AI ("AI packs"): deliver models install-time, fast-follow or on-demand; "Individual AI packs can be up to 1.5GB"; cumulative app size limit 4 GB; device targeting by "System on chip", "Device model", "Device RAM" and system features (AGP 8.10+, experimental flag); needs AGP 8.8+; delivery library `com.google.android.play:ai-delivery:0.1.1-alpha01`; downloads over 200 MB wait for Wi-Fi or user consent; AI packs "only contain models. Java, Kotlin, and native libraries are not allowed"; devices that match no group get the default variant, which can be empty. — [Play for On-device AI](https://developer.android.com/google/play/on-device-ai)
- Feature modules can carry code/native libraries and be delivered on demand or conditionally (device features, minimum API level, country, device groups) on API 21+; 50+ modules per device may cause performance issues. — [Play Feature Delivery](https://developer.android.com/guide/playcore/feature-delivery); [Play for On-device AI](https://developer.android.com/google/play/on-device-ai)
- react-native-executorch downloads models at runtime with a progress callback and automatic caching rather than bundling them. — [react-native-executorch README](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/README.md)

#### System OCR vs shipping your own
- Ente (privacy-focused photo app) found Apple's Vision framework good on iOS but rejected ML Kit on Android because of its "dependence on Google Play Services and closed nature", and instead ported PaddleOCR v5 to ONNX Runtime. — [Ente blog: The best open-source Android OCR](https://ente.com/blog/ocr/) [search summary]
- System OCR quality can change under the app: an Apple developer-forum thread reports a major regression in the `.accurate` VNRecognizeTextRequest model on iOS 27 (iPad), with `.fast` unchanged. — [Apple Developer Forums thread 851862](https://developer.apple.com/forums/thread/851862) [search summary]
- Apple's two recognition paths: `.fast` uses character detection, `.accurate` a neural network over strings and lines, and `.accurate` is the default. — [Apple: Recognizing text in images](https://developer.apple.com/documentation/vision/recognizing-text-in-images.md) [search summary]
- Unbundled ML Kit depends on Google Play services, which since July 2026 supports only Android 7.0+. — [Android Authority](https://www.androidauthority.com/google-android-6-marshmallow-support-ended-3691168/) [search summary]

### Inferences
- Approximate minimum download cost of a complete Latin-script OCR feature per ABI (sums of the cited component sizes; runtime figures are vendor claims of varying age): Apple Vision 0; ML Kit unbundled about 0.3 MB; ML Kit bundled about 4 MB; MNN (about 0.8 MB) or TNN (about 0.4 MB) plus PP-OCRv6_tiny (6.3 MB fp32; an INT8 detector would trim it further) about 6-7 MB; Paddle-Lite plus PP-OCRv2/v3 slim (4.6-5.9 MB) about 8-10 MB; Tesseract (native library size not verified) plus 3.9 MB fast data; ONNX Runtime plus PP-OCRv5_mobile (20.7 MB) or PP-OCRv6_small (30 MB) plus OpenCV well above 30 MB.
- For an existing app that must reach old phones, the cheapest design is: keep the native runtime in the base module (or an install-time feature module, because AI packs cannot hold `.so` files) and ship models as fast-follow/on-demand asset or AI packs, using RAM/SoC device targeting to give low-RAM devices the tiny model set and stronger devices the small/mobile set.
- System OCR minimises bytes and maintenance but gives up control: no pinning of model version (iOS regression report), no availability on non-GMS Android devices, and a floor that moves with Play services.

### Gaps
- iOS delivery mechanisms (On-Demand Resources, Background Assets, Apple-hosted asset packs) and their size limits and minimum iOS versions were not verified in this session (Apple documentation not fetched).
- Tesseract4Android AAR / native-library size, current ncnn / ONNX Runtime / LiteRT per-ABI sizes and OpenCV's contribution were not found; a measured end-to-end APK-size delta for any OCR stack was not found.
- ML Kit's exact size table could not be read directly (developers.google.com blocked), including sizes for non-Latin scripts.
- Google Play's exact maximum-size table (support.google.com) was not fetched; only the 4 GB compressed-download and 1.5 GB AI-pack figures were confirmed.

## 6. Mobile web and cross-platform options on old phones (Tesseract.js, ONNX Runtime Web, WebGPU/WebNN, Transformers.js; Flutter and React Native plugins that work offline, and their overhead)

### Takeaway
On old phones the mobile web means WebAssembly on the CPU only: WebGPU exists in Chrome for Android only from Android 12 and in Safari only from iOS 26, so it is unavailable to every "old" tier; Tesseract.js (v7) and tesseract-wasm are the small, mature browser options, and PaddleOCR now publishes an official ONNX-Runtime-Web SDK, but none publishes phone timings. Cross-platform frameworks have themselves raised their floors (Flutter: Android API 24 / iOS 15; react-native-executorch: API 26 / iOS 17), so the offline plugins that still reach old devices are thin bridges to native ML Kit (minSdk 21) or to self-built native runtimes.

### Cited Findings
- **WebGPU availability**: Chrome for Android 121 on Android 12+ with ARM/Qualcomm/Intel GPUs; Imagination GPUs from Chrome 139 on Android 16+; Samsung Xclipse still to be determined; Safari supports WebGPU by default in iOS 26 / iPadOS 26; Firefox for Android is behind a flag. — [gpuweb Implementation Status](https://github.com/gpuweb/gpuweb/wiki/Implementation-Status)
- **WASM SIMD availability**: SIMD-enabled builds work in "Chrome >= 91, Firefox >= 90, Safari >= 16.4"; a separate fallback binary is needed for browsers without SIMD. — [tesseract-wasm README](https://raw.githubusercontent.com/robertknight/tesseract-wasm/main/README.md)
- **tesseract-wasm**: "The library and English training data require a ~2.1MB download (with Brotli compression)". — [tesseract-wasm README](https://raw.githubusercontent.com/robertknight/tesseract-wasm/main/README.md)
- **Tesseract.js**: releases v7.0.0 ("15 Dec", 2025 inferred), v6.0.1, v6.0.0; v7 reduces runtimes about 15-35% versus v6 and adds a `relaxedsimd` build; v6 fixed memory leaks where memory "would rise over time, eventually leading to a crash" and disabled all output formats except text by default; v5 made files "54% smaller for English, 73% smaller for Chinese", cut first-run time about 50% and lowered memory use. — [tesseract.js releases](https://github.com/naptha/tesseract.js/releases); [tesseract.js README](https://raw.githubusercontent.com/naptha/tesseract.js/master/README.md)
- Tesseract.js performance guidance: "the majority of runtime may be attributable to setup steps"; reuse workers and use a scheduler with a fixed pool because "each Tesseract.js worker uses a high amount of memory" and a worker per job "is likely to cause crashes due to resource limitations"; a first load is "~15MB in code and data"; default English data is about 2 MB; four core files exist (plain/SIMD x full/LSTM-only); speed-oriented data can be selected via `langPath` (`4.0.0_fast`) but was not benchmarked by the maintainers. — [tesseract.js performance.md](https://raw.githubusercontent.com/naptha/tesseract.js/master/docs/performance.md)
- **PaddleOCR.js (official)**: npm `@paddleocr/paddleocr-js`; "manages OpenCV.js and ONNX Runtime internally"; backends `"auto"` and `"wasm"`; documented models `PP-OCRv5_mobile_det` and `PP-OCRv5_mobile_rec`; hosts must set COOP/COEP headers "when enabling threaded WASM or WebGPU"; example uses `numThreads: 2`, `simd: true`; optional worker mode; reports `detMs`, `recMs`, `totalMs` per call; no latency numbers, model sizes or mobile notes. — [PaddleOCR browser.en.md](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/inference_deployment/cross_platform/browser.en.md)
- **gutenye/ocr**: JavaScript OCR on PaddleOCR + ONNX Runtime for Node, browser, React Native and C++; supports PP-OCRv4 and PP-OCRv5; the browser needs developer-hosted model files and the README steers browsers to the smaller PP-OCRv4 models; no performance numbers. — [gutenye/ocr README](https://raw.githubusercontent.com/gutenye/ocr/main/README.md)
- **Transformers.js** (README pins 4.3.2): "By default, when running in the browser, the model will be run on your CPU (via WASM)"; WebGPU via `device: 'webgpu'` is "still experimental in many browsers"; dtypes "fp32" (default for WebGPU), "fp16", "q8" (default for WASM), "q4"; OCR-relevant support is transformer models (TrOCR, image-to-text, document QA). — [transformers.js README](https://raw.githubusercontent.com/huggingface/transformers.js/main/README.md)
- A hobby evaluation reports PaddleOCR matching or beating Tesseract on synthetic pages when both run in a browser via WebAssembly. — [paper-trail issue 101](https://github.com/brycewalls/paper-trail/issues/101) [search summary]
- **Flutter**: `google_mlkit_text_recognition` is a bridge ("Think of this plugin as a bridge between your app and Google's native ML Kit APIs") over `MethodChannel`; minSdkVersion 21, targetSdk/compileSdk 36; iOS minimum 15.0, Xcode 15.3+, no 32-bit iOS; Latin is bundled by default on Android with other scripts as extra dependencies (16.0.1); with the Swift-Package build only Latin is supported on iOS. — [google_mlkit_text_recognition README](https://raw.githubusercontent.com/flutter-ml/google_ml_kit_flutter/master/packages/google_mlkit_text_recognition/README.md)
- Flutter itself supports Android API 24-37 (arm32 and arm64) and iOS 15-27. — [Flutter supported platforms](https://raw.githubusercontent.com/flutter/website/main/sites/docs/src/content/reference/supported-platforms.md)
- **React Native**: `@react-native-ml-kit/text-recognition` exposes `TextRecognition.recognize(imageURL, script?)` with Latin default and Chinese, Devanagari, Japanese, Korean scripts. — [react-native-ml-kit text-recognition README](https://raw.githubusercontent.com/a7medev/react-native-ml-kit/main/text-recognition/README.md)
- `react-native-executorch` (fully offline after model download; PP-OCRv6 fused pipeline) needs iOS 17.0+ / Android 8.0+ (minSdk 26), React Native 0.83+ or Expo SDK 55+ development builds, New Architecture; Expo Go unsupported. — [react-native-executorch README](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/README.md)
- chineseocr_lite documents Android demos on ONNX Runtime, ncnn (CPU and Vulkan) and MNN, plus a third-party TNN demo for iOS/Android (ARMv7/ARMv8 CPU, OpenCL/Metal GPU). — [chineseocr_lite README](https://raw.githubusercontent.com/DayBreak-u/chineseocr_lite/onnx/README.md)

### Inferences
- Any phone that counts as "old" here (Android 5-11, iOS 12-16) has no WebGPU; a browser OCR feature must budget for single- or dual-threaded WASM, and threaded WASM additionally needs cross-origin isolation headers. iOS devices stuck on iOS 15 (Safari 15) also lack WASM SIMD (Safari 16.4+).
- For mobile web on weak hardware the evidence favours the smallest payload and a classic engine (tesseract-wasm about 2.1 MB, or Tesseract.js LSTM-only core plus fast data) for clean printed text, with PaddleOCR.js / ONNX Runtime Web (PP-OCRv5 mobile models, about 20 MB of weights) reserved for stronger devices or harder images. No measurement was found to confirm the speed difference.
- Flutter and React Native OCR plugins add little inference overhead when they are bridges to native engines (ML Kit, ExecuTorch); their cost on old phones is framework baseline memory (ExecuTorch OCR app peaks of 372-888 MB include the React Native app) and framework OS floors (Flutter API 24 / iOS 15), not the channel call. This is reasoning from architecture, not a measured comparison.
- The only cross-platform route that still reaches Android 5-6 is native code behind a thin binding (a custom plugin over ncnn/MNN/Tesseract), and then only if the framework itself supports those OS versions (current Flutter does not).

### Gaps
- No published timing of Tesseract.js, tesseract-wasm, PaddleOCR.js or ONNX Runtime Web OCR on any phone, old or new; no mobile-browser memory ceilings (for example iOS Safari WASM limits) were verified.
- ONNX Runtime Web documentation (WASM SIMD/threads flags, WebGPU/WebNN execution providers) could not be fetched; WebNN availability on phones was not researched.
- No measured Flutter / React Native bridging overhead for OCR (image copy and serialization) was found.
- Fully offline Flutter plugins based on PaddleOCR/ncnn or Tesseract were not surveyed (search budget exhausted); React Native's own minimum OS versions were not confirmed from the React Native README.

## 7. What do independent head-to-head comparisons on actual phones conclude about ML Kit vs Tesseract vs PP-OCR mobile vs others, especially on budget devices?

### Takeaway
Independent phone-based comparisons are few and none measures latency on a budget Android device: the one recent accuracy study found ML Kit and PP-OCRv4 statistically tied on Android photos (75.5% vs 74.7% field-level F1), a 2021 iPhone 12 test found ML Kit about 6x faster than Apple Vision, and an older test on a 2 GB Galaxy J7 found Tesseract and ML Kit each winning on different images. The practical pattern from teams shipping OCR is platform-native OCR on iOS (Vision) and either ML Kit or a PaddleOCR port on Android, chosen on dependency and openness grounds rather than on a measured speed gap.

### Cited Findings
- "Benchmarking on-device OCR" (personal engineering blog): on phone photos, ML Kit scored 75.5% field-level F1 on Android and PaddleOCR PP-OCRv4 74.7%, a gap the author treats as within sampling noise; no latency and no phone models are reported. — [prasad.tech](https://prasad.tech/blog/benchmarking-on-device-ocr/) [search summary]
- Fritz AI (c. 2018-2019) compared Tesseract and ML Kit on a Samsung Galaxy J7 with 2 GB RAM: Tesseract did better on many images, ML Kit on others; the summary quotes "ML Kit was better in this case, as it had a higher correctness rate" for one case. — [Fritz AI: Choose the Right On-Device Text Recognition SDK on Android](https://fritz.ai/choose-the-right-on-device-text-recognition-sdk-on-android/) [search summary]
- bitfactory (30 Jun 2021, iPhone 12): ML Kit about 0.05 s per image vs Apple Vision about 0.31 s; Vision judged better on rotated text and API features; no F1. — [bitfactory comparison (mirror)](https://project-aries-cdl.pages.dev/raw/articles/ocr-framework-comparison-vision-mlkit) [search summary]
- Ente: on Android "Google's ML Kit was the only available implementation with good results" but its Play Services dependence and closed nature ruled it out; they ported PaddleOCR v5 to ONNX Runtime; Apple Vision was used on iOS. No F1 or latency figures. — [Ente blog](https://ente.com/blog/ocr/) [search summary]
- An unsourced GitHub community post claims ML Kit is 20-40% more accurate than Tesseract on Android, with no methodology. — [GitHub community discussion 178210](https://github.com/orgs/community/discussions/178210) [search summary]
- E-ARMOR (2025) found a PaddleOCR-based edge OCR system had the best F1 (0.46) and 0.17 s per image among compared systems, but it ran on NVIDIA T4 GPUs and did not include ML Kit or Apple Vision. — [E-ARMOR, arXiv 2509.03615](https://arxiv.org/html/2509.03615v1) [search summary]
- A vendor post reports about 680 ms for a receipt on an iPhone 13 Pro with its own monolithic pipeline (not an independent benchmark). — [omr.it.com](https://omr.it.com/blog/incremental-ocr-streaming-80ms-first-token-latency/) [search summary]
- PaddleOCR's own tiers on its in-house benchmark: PP-OCRv6_tiny reaches detection Hmean 80.6 / recognition 73.5 versus PP-OCRv5_mobile 75.2 / 73.7, at 6.3 MB vs 20.7 MB (vendor data, not independent). — [PaddleOCR PP-OCRv6 doc](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/docs/version3.x/algorithm/PP-OCRv6/PP-OCRv6.en.md)

### Inferences
- On accuracy, ML Kit and PP-OCR mobile-class models are in the same band on ordinary phone photos; the decision between them on Android is driven by dependencies (Play services, API 24 floor, closed model), script coverage and app size rather than by a demonstrated quality gap. Tesseract remains competitive only on clean, well-binarised printed text (the mixed 2018 result and its design as a document engine); this is consistent with, but not proven by, the cited tests.
- No source supports a claim that any engine is "X times faster than ML Kit on budget Android"; anyone needing that number must measure it. The closest public latency data are flagship-class (section 3).

### Gaps
- No independent study was found that measures latency and memory of ML Kit, Tesseract and PP-OCR mobile on the same budget Android phone (Snapdragon 4xx/6xx, Helio, Unisoc) or on old iPhones.
- The prasad.tech and Fritz AI articles were not opened (hosts not on the allowlist; search budget exhausted), so their methodology, device lists and any per-engine timings are unverified.
- Academic comparisons on low-resource-language mobile OCR (for example Indic, Amharic, Arabic scripts on low-end devices) were not retrieved because arXiv and further searches were unavailable.

## 8. Based on the evidence, what device tiers make sense and what OCR approach is evidenced to work at each tier?

### Takeaway
The evidence supports four tiers defined by CPU generation and OS floor rather than by RAM alone: (1) very old (Android 5-7 or 32-bit, Cortex-A53/A7 only, 1-2 GB; A9/A10 iPhones), where only system OCR, Tesseract-fast or a tiny detector-free/low-resolution CNN pipeline on ncnn/MNN is realistic and multi-second full-page times must be expected; (2) old (2017-2019 A72/A73/A75 phones, 3-4 GB; A11 iPhones), where PP-OCR mobile/tiny pipelines run in roughly 0.4-1.2 s; (3) modern mid-range (ARMv8.2+, 4-8 GB; A12-A15), where PP-OCRv6-small-class models run in 0.15-0.45 s on CPU and far faster on Apple's Neural Engine; (4) flagships, where GPU/NPU paths give tens of milliseconds.

### Cited Findings
- Tier-defining platform facts: Play services (ML Kit unbundled) requires Android 7.0+; LiteRT 2.3 and Flutter require API 24; PaddleOCR's SDK and react-native-executorch require API 26; ExecuTorch is arm64-only and iOS 17+; the Core ML Neural Engine exists only on A12+; FP16 CPU paths exist only on ARMv8.2 SoCs (Snapdragon 845 and later in Paddle Lite's tables); Android Go requires 2 GB from Android 13. — [Android Authority](https://www.androidauthority.com/google-android-6-marshmallow-support-ended-3691168/) [search summary]; [LiteRT v2.3.0 notes](https://github.com/google-ai-edge/LiteRT/releases/tag/v2.3.0); [PaddleOCR app build.gradle.kts](https://raw.githubusercontent.com/PaddlePaddle/PaddleOCR/main/deploy/ppocr-android/app/build.gradle.kts); [react-native-executorch README](https://raw.githubusercontent.com/software-mansion/react-native-executorch/main/README.md); [using-executorch-ios.md](https://raw.githubusercontent.com/pytorch/executorch/main/docs/source/using-executorch-ios.md); [hollance/neural-engine](https://raw.githubusercontent.com/hollance/neural-engine/master/docs/supported-devices.md); [Paddle-Lite benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/performance/benchmark.md); [Android (Go edition)](https://developer.android.com/guide/topics/androidgo)
- Tier 1 CPU evidence: Snapdragon 410 (4x A53 1.2 GHz), 4 threads: mobilenet_v3 63.90 ms, shufflenet_v2 40.66 ms; Snapdragon 625 (8x A53), 1 thread: MobileNetV3_small 39.08 ms FP32 / 22.83 ms INT8 (arm64), 37.74 / 26.86 ms (armv7); MobileNetV3_large 96.11 / 66.76 ms; iPhone 5S (A7), 2 threads: mobilenet_v3 53.12 ms. — [ncnn benchmark README](https://raw.githubusercontent.com/Tencent/ncnn/master/benchmark/README.md); [Paddle-Lite benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/performance/benchmark.md)
- Tier 1 software evidence: ncnn PP-OCRv5 demo targets API 21 and armeabi-v7a with detectors converted at 256-320 px; Tesseract4Android supports API 21 with 3.92 MB fast English data; MNN documents Android 4.3+/ARMv7a with an 800 KB core library. — [nihui/ncnn-android-ppocrv5](https://github.com/nihui/ncnn-android-ppocrv5); [Tesseract4Android README](https://raw.githubusercontent.com/adaptech-cz/Tesseract4Android/master/README.md); [tessdata_fast eng](https://github.com/tesseract-ocr/tessdata_fast/blob/main/eng.traineddata); [MNN README](https://raw.githubusercontent.com/alibaba/MNN/master/README.md)
- Tier 2 CPU evidence: Snapdragon 835, 4 big threads: mobilenet_v2 19.87-29.41 ms, mobilenet_v3 24.79 ms; INT8 MobileNetV3_large 30.57 ms vs 41.74 ms FP32 at 1 thread; Kirin 970 4 threads mobilenet_v3 23.07 ms; Pixel 2 / Pixel 3a multi-thread MobileNet v3 Large 16 / 24 ms, v3 Small 6 / 8 ms; Snapdragon 675 2 threads mobilenet_v2 26.08 ms. — [Paddle-Lite v2.6 benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/release/v2.6/docs/benchmark/benchmark.md); [ncnn benchmark README](https://raw.githubusercontent.com/Tencent/ncnn/master/benchmark/README.md); [Paddle-Lite benchmark.md](https://raw.githubusercontent.com/PaddlePaddle/Paddle-Lite/develop/docs/performance/benchmark.md); [XNNPACK README](https://raw.githubusercontent.com/google/XNNPACK/master/README.md)

### Inferences
(The tier table is the researcher's synthesis of the cited evidence; latency ranges marked "est." are extrapolations, not measurements.)

| Tier | Typical hardware / OS | What the evidence says works | Expected speed |
|---|---|---|---|
| 1. Very old | Android 5-7, armeabi-v7a or A53-only SoCs (Snapdragon 410/425/430/450/625, MT6737/39, Helio A22/P22, SC9863A), 1-2 GB, Android Go; iPhone 6s/7/SE-1 (A9/A10, iOS 15) | Android: self-shipped **ncnn or MNN** (API 21, armv7) with the smallest models (PP-OCRv6_tiny 6.3 MB, or PP-OCRv2/v3 slim 4.6-5.9 MB on legacy Paddle-Lite), detector long side capped at 320-640 or detector skipped for fixed fields, 2-4 threads; **Tesseract4Android + tessdata_fast** for clean printed text; ML Kit only on API 24+ with Play services. iOS: **Apple Vision** (zero bytes) or Core ML `neuralnetwork`/self-built C++ on CPU, since ML Kit (15.5) is the only third-party SDK whose floor fits | est. 1.5-3+ s for a multi-line image at about 640 px; est. 0.1 s per line for recognition-only; INT8 gives about 1.2-1.7x |
| 2. Old | 2017-2019: Snapdragon 660/675/835/845, Kirin 970, Exynos 8895/9810, Helio P60/G80; 3-4 GB; Android 8-10; iPhone 8/X (A11, iOS 16) | Everything in tier 1, plus **ML Kit** (bundled about 4 MB or unbundled about 260 KB), PP-OCRv5_mobile / PP-OCRv6_tiny via ncnn (arm64), PaddleOCR's ONNX Runtime SDK on Android 8+; CPU only (GPU not reliably faster); A11 iPhones still have no Core ML Neural Engine | est. 0.4-1.2 s full pipeline (420 ms measured on Snapdragon-855-class; Snapdragon 835 about 2.6x slower) |
| 3. Modern mid-range | 2020-2023: ARMv8.2+ (A55/A76+) SoCs with dot-product and FP16, 4-8 GB, Android 11-14; iPhone XS to iPhone 14 / SE 2-3 (A12-A15) | PP-OCRv6_small / PP-OCRv5_mobile on ONNX Runtime, LiteRT or ExecuTorch (XNNPACK), INT8 detector + FP32 recognizer, FP16 where supported; on iOS Core ML with the Neural Engine or Apple Vision | measured 425 ms (S20+, CPU), 167 ms (iPhone SE 3, CPU), 9.5 ms (iPhone SE 3, Core ML) |
| 4. Flagship | 2024+: Snapdragon 8 Elite class, Tensor G5, A17-A19; 8-16 GB | Same models with GPU (Vulkan/ML Drift) or NPU delegates; larger models become affordable | measured 39-119 ms (Vulkan), 6.7 ms (Core ML), 107-188 ms (CPU) |

- **Smallest setup that still works on old phones** (evidence-weighted): system OCR where it exists (Vision; ML Kit unbundled at about 0.3 MB on API 24+ GMS devices). When models must be shipped: a sub-megabyte C++ runtime that still supports ARMv7 (MNN about 0.8 MB, or ncnn trimmed with its minimal-build switches) plus PP-OCRv6_tiny (1.9 MB detector + 4.4 MB recognizer), or for clean Latin print Tesseract with 3.9 MB fast data.
- **Fastest setup on old CPUs** (evidence-weighted): avoid work rather than accelerate it, in this order: skip detection with a capture guide, cap detector input, use the tiny/slim detector, run 2-4 threads on the best cores, quantize the detector to INT8, keep the recognizer FP32 unless accuracy is verified. GPU, FP16 and NPU paths only pay off from tier 3 upward.
- RAM is a secondary but real constraint: the only published peak-memory figures (0.37-0.89 GB for a React Native app running PP-OCRv6-small) imply that tier-1 devices need a native pipeline, small input tensors and one loaded model at a time; no measurement confirms how low a native ncnn/MNN PP-OCR tiny pipeline goes.

### Gaps
- The tier-1 and tier-2 latency ranges are extrapolated from backbone ratios and one Snapdragon-855-class measurement; no public end-to-end OCR measurement on tier-1 hardware was found to validate them.
- No evidence was found for OCR on A9-A11 iPhones (Vision or Core ML timings), nor for peak memory of native (non-React-Native) OCR pipelines on 1-2 GB Android devices.
- Tier boundaries by RAM could not be tied to market-share data (no public RAM distribution found); the device-to-maximum-iOS mapping used for the iPhone rows is from the researcher's background knowledge and was not sourced in this session.
- PP-OCRv6_tiny's accuracy is vendor-reported on an in-house set and its behaviour after INT8 quantization on ncnn/MNN was not found.
