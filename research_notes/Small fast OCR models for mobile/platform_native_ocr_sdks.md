## 1. Google ML Kit Text Recognition v2: latest version, scripts, app-size impact, minimum OS, low-end device support, acceleration, latency

### Takeaway
ML Kit Text Recognition v2 is still a five-script recognizer (Latin, Chinese, Devanagari, Japanese, Korean) with no Arabic or Cyrillic script model exposed and nothing announced; the smallest footprint is the unbundled Google Play services variant (about 260 KB per script in the APK, model delivered by Play services) versus about 4 MB per script per architecture when bundled. It needs only Android API 21 and iOS 15.5 (64-bit), but Google publishes no latency numbers that I could find, and the library looks to be in maintenance mode (bundled artifacts unchanged at 16.0.1, iOS unchanged since June 2025).

**App-size impact and model download behaviour**
- Android guide table: unbundled (Play services) = "About 260 KB size increase per script architecture"; bundled = "About 4 MB size increase per script per architecture" [snippet, returned identically by two separate searches] — [Recognize text in images with ML Kit on Android (v2)](https://developers.google.com/ml-kit/vision/text-recognition/v2/android)
- Release notes describe the unbundled impact as "shrinked to only ~260 KB" [snippet] — [ML Kit release notes](https://developers.google.com/ml-kit/release-notes)

### Inferences
- "Latest version as of November 2026" is best stated as: bundled Android 16.0.1 (all five scripts; no evidence of a newer bundled build), unbundled Android 19.0.2 (Latin) / 16.0.2 (other scripts) from the October 26, 2026 release, and iOS `MLKitTextRecognition` 7.0.0 inside `GoogleMLKit` 9.0.0 (June 27, 2025). The October 2026 bump is snippet-level only.
- The script list has not changed since v2 launched; combined with a 17-month-old iOS build and Google's 2025–2026 announcements being about Gemini Nano APIs (section 4), classic text recognition appears to be in maintenance mode. Nothing found suggests Arabic, Cyrillic, Thai or Hebrew recognizers are in beta or planned.
- Smallest Android option: unbundled Latin only, roughly 260 KB of APK growth. The cost is a hard dependency on Google Play services and a model download before first use, so it is not "offline from first launch". Bundled costs about 4 MB per script per ABI; with Android App Bundles only one ABI is delivered per device, so Latin-only bundled is roughly 4 MB on the user's phone.
- For old Android phones the floor (API 21, Android 5.0) is as low as any option in this report. For old iPhones ML Kit's floor (iOS 15.5, arm64) is higher than Apple Vision's (iOS 13), and ML Kit adds app size where Vision adds none, so on iOS ML Kit only makes sense for cross-platform output parity.
- The frame-skipping defaults in camera wrappers suggest per-frame OCR at full camera frame rate is not expected even on current devices; budget for a few recognitions per second on low-end hardware and measure on target devices.

## 2. Apple Vision and VisionKit: OS/device support per API, languages per OS version, speed on older iPhones, handwriting, 2025–2026 additions

### Takeaway
Apple's text recognition ships inside the OS (no app-size cost) from iOS 13, with a `.fast` path (character detector plus small model, meant for real time) and an `.accurate` path (neural, line-based); language coverage grew from English only (iOS 13) to 18 identifiers (iOS 18), "26 languages" (iOS 26) and "over 30" for the iOS 27 OCR tool. Newer surfaces raise the hardware floor (Live Text API and DataScanner need iOS 16 and an A12 chip; the Swift API needs iOS 18; document structure needs iOS 26), and developers report a serious `.accurate` accuracy regression on iOS 27 that Apple had not answered as of 2026-11-19.

### Cited Findings

**API availability (all [fetched] from Apple documentation on 2026-11-19)**

**How fast and accurate differ**
- Fast: "uses the framework's character-detection capabilities to find individual characters, and then uses a small machine learning model to recognize individual characters and words"; accurate: "uses a neural network to find text in terms of strings and lines"; either can apply an optional language-correction phase [fetched] — [Recognizing Text in Images](https://developer.apple.com/documentation/vision/recognizing-text-in-images)
- WWDC19: "The fast path is meant for real-time reading and it's optimized for that. But the accurate path is more likely to be used in an asynchronous fashion"; "the fast path also uses less memory because it doesn't need to run a large neural network"; for rotated, perspective-distorted or stylized text "the accurate path gives you much broader support" [fetched] — [WWDC19 session 234](https://developer.apple.com/videos/play/wwdc2019/234/)
- WWDC19 tuning levers: language correction "does not come for free. It does take some processing time and of course it uses a little bit of memory"; with `minimumTextHeight` "the input image will be downsized, and the execution time will be smaller... the memory usage will go down"; a region of interest "enhances the performance" [fetched] — [WWDC19 session 234](https://developer.apple.com/videos/play/wwdc2019/234/)
- WWDC21: "In the Fast path, we have a Latin-character recognizer"; in the accurate path "a completely different model gets used when we have to recognize Chinese"; "I don't have support in the Fast path for Chinese" [fetched] — [WWDC21 session 10041](https://developer.apple.com/videos/play/wwdc2021/10041/)
- Automatic language detection (`automaticallyDetectsLanguage`) works "only for accurate recognition mode" and "can occasionally get this wrong" (WWDC22) [fetched] — [WWDC22 session 10024](https://developer.apple.com/videos/play/wwdc2022/10024/)
- Compute units: "To reduce our memory footprint, Vision will remove CPU and GPU support for some requests on devices with a Neural Engine... the Neural Engine is the most performant option"; check with `supportedComputeDevices()` (WWDC24) [fetched] — [WWDC24 session 10163](https://developer.apple.com/videos/play/wwdc2024/10163/)
- Privacy: "all of Vision's processing happens on the user's device" [fetched]; "all vision APIs run entirely on-device" (WWDC25) [fetched] — [Recognizing Text in Images](https://developer.apple.com/documentation/vision/recognizing-text-in-images); [WWDC25 session 272](https://developer.apple.com/videos/play/wwdc2025/272/)

### Inferences
- App-size impact of Apple Vision is zero and there is no model download: the recognizer ships with the OS. That makes it the smallest option on iPhone by construction.
- "26 languages" in iOS 26 is consistent with the 25-language Live Text list plus Arabic; this is my reconciliation, not something Apple states.
- For old iPhones the practical matrix follows from the OS floors above. Devices stuck on iOS 13–15 can use only `VNRecognizeTextRequest` revisions 1–2 (English, then English/French/Italian/German/Spanish/Portuguese/Chinese); Japanese, Korean, Russian and Ukrainian need iOS 16; Thai and Vietnamese appear from iOS 17; Arabic appears in the iOS 18 list. Which iPhone models top out at which iOS version is general knowledge I did not source this session (see Gaps).
- For speed on old hardware, `.fast` with a region of interest, a `minimumTextHeight` and language correction off is the configuration Apple itself describes as the real-time one; `.accurate` should be treated as a still-image, asynchronous path (seconds on pre-Neural-Engine devices according to 2019 developer reports).
- Because Apple swaps models under an unchanged revision number, OCR accuracy can change with an OS update without any app change. Apps that depend on Vision should keep a regression test set and, for iOS 27, consider the reported workarounds or the unaffected `.fast` path.

## 4. On-device GenAI stacks (Gemini Nano via ML Kit GenAI APIs / AICore; Apple Intelligence): OCR-relevant capabilities and eligible devices

### Takeaway
Both platforms gained explicit OCR-style image understanding in their on-device LLM stacks during 2026 (Gemini Nano 4 through ML Kit's Prompt API; image inputs plus a Vision `OCRTool` in Apple's Foundation Models framework on iOS 27), but only on recent flagship-class hardware (AICore-enabled Android devices; iPhone 15 Pro and later). ### Inferences
- BlinkID's small binary is partly explained by models being fetched from a CDN at first run by default; pre-bundling the resources for offline-first use would add to the app size by an amount the README does not state.
- None of these SDKs is a size or cost win over ML Kit or Apple Vision for plain text OCR. Their value is in tuned capture flows for specific document types, vendor support, and (for Anyline, Scanbot, Dynamsoft) uniform behaviour across Android and iOS.
- Scanbot's general OCR being Tesseract-based for most languages places it outside this report's "platform-native" class for multi-language text.

### Gaps
- Vendor sites were blocked and the searches for Microblink pricing, Klippa on-device OCR and Nutrient's OCR component could not be run. Not established: whether Klippa's OCR runs on-device or in its cloud; Nutrient OCR language-pack sizes and pricing; current SDK sizes for Scanbot, Dynamsoft and ABBYY; minimum OS versions for Anyline, Scanbot and Dynamsoft; any explicit low-end-device claims.
- No vendor-published or independent accuracy/speed benchmark for any of these SDKs was found.
- Anyline's "up to 90 MB" figure is from an older SDK generation (v42 versus v56 today) and may not reflect current packaging.

## 6. Independent comparisons of ML Kit, Apple Vision, Tesseract and PaddleOCR on-device (accuracy and speed)

### Takeaway
Only one independent head-to-head covering both platform engines surfaced: a blog benchmark on phone photos in which Apple Vision scored 85.4% field-level F1 against 75.5% for ML Kit and 74.7% for PaddleOCR PP-OCRv4 (a statistical tie with ML Kit). It reports no latency, and no study was found that measures all four engines on the same device and test set.

### Cited Findings
- prasad.tech, "Benchmarking on-device OCR": field-level F1 on phone photos run "through a real mobile pipeline" (React Native); Apple Vision 85.4% end to end and 94.1% on clean captures ("instant and free"); on Android, ML Kit 75.5% and PaddleOCR PP-OCRv4 74.7%, which the author calls a statistical tie ("+0.8, within sampling noise"); "The Vision and ML Kit rows share the identical 778-image set, so that head-to-head is exact"; the post also covers tesseract.js and cloud vision models such as Gemini 2.5 Flash [snippet; publication date, devices and the Tesseract/cloud numbers were not captured] — [prasad.tech benchmark](https://prasad.tech/blog/benchmarking-on-device-ocr/)
- Same-engine, cross-OS test by an app developer (Oct 2026): about 26,500 video frame grabs of cinema-camera overlays, `VNRecognizeTextRequest` `.accurate`, en-US, language correction off, fixed region of interest: 99.7% of values read correctly on iOS 26 versus 65% on iOS 27, with `.fast` unchanged [fetched] — [Apple forum thread 851862](https://developer.apple.com/forums/thread/851862)
- Baseline context only (desktop CPU, vendor blog, 2026): Tesseract took 0.07–0.26 s per image, 5–23 times faster than PaddleOCR's default medium model, while PaddleOCR made fewer errors on a skewed phone-style photo, a faded receipt and Chinese text [snippet] — [docsapi.co comparison](https://docsapi.co/resources/blogs/paddleocr-vs-tesseract-vs-docsapi)
- An assistive-technology study that ranks "Google Vision" highest used Google's cloud Vision OCR, not on-device ML Kit, so it does not transfer [snippet] — [arXiv 2602.02223](https://arxiv.org/html/2602.02223v1)

### Inferences
- On the one comparable data point, Apple Vision is roughly 10 F1 points ahead of ML Kit on real phone photos, and ML Kit is on par with a shipped PP-OCRv4 model. That is a single author's benchmark and should be presented as indicative.
- The iOS 27 figures show that "Apple Vision accuracy" is not a fixed quantity: the same API and revision produced very different results across OS versions for one workload. Any comparison should record the OS version.

### Gaps
- No independent latency comparison between ML Kit, Apple Vision, Tesseract and PaddleOCR on phones was found, and none on old or low-end devices.
- The prasad.tech page could not be opened, so its date, device models, OS versions, dataset composition and the Tesseract and cloud-model rows are missing. The comparison also crosses platforms (Vision on iOS, ML Kit and PaddleOCR on Android), so camera and device differences are confounded.
- No peer-reviewed study including both ML Kit and Apple Vision on-device was found; a follow-up search of the HalalBench paper (arXiv 2604.22754), which mentions ML Kit, could not be run.

## 8. Known limitations: customisation, unsupported scripts, licence and Play services dependency, privacy claims

### Takeaway
Neither platform recognizer can be retrained or swapped: ML Kit exposes only a choice of five script models and Vision only language hints, custom words and a recognition level, with Apple free to change the model under an unchanged revision number. The main structural constraints are ML Kit's missing Arabic/Cyrillic/Thai/Hebrew scripts and Play services dependency for its smallest variant, Vision's OS-version-dependent languages and accuracy, and device eligibility for the GenAI routes.

### Cited Findings
- ML Kit offers custom-model variants only for image labeling and object detection (`ImageLabelingCustom`, `ObjectDetectionCustom`); the text-recognition pods have no custom variant [fetched] — [googlesamples/mlkit Podfile](https://raw.githubusercontent.com/googlesamples/mlkit/master/ios/quickstarts/vision/Podfile)
- ML Kit binaries are closed source; wrapper maintainers "do not have access to the source code of their native APIs" and direct bug reports to Google [fetched] — [google_mlkit_text_recognition README](https://raw.githubusercontent.com/flutter-ml/google_ml_kit_flutter/master/packages/google_mlkit_text_recognition/README.md)
- ML Kit script coverage stops at Latin, Chinese, Devanagari, Japanese and Korean; Arabic is absent from the supported-language tables [snippet] — [Text recognition v2: supported languages](https://developers.google.com/ml-kit/vision/text-recognition/v2/languages)
- The unbundled ML Kit variant is served through Google Play services [snippet, paraphrased] and, in a wrapper's words, "requires internet on first use" [fetched] — [ML Kit installation paths](https://developers.google.com/ml-kit/tips/installation-paths); [rn-mlkit-ocr README](https://raw.githubusercontent.com/ahmeterenodaci/rn-mlkit-ocr/main/README.md)
- ML Kit on iOS: CocoaPods-only distribution from Google, no arm64 simulator slice, iOS 15.5 minimum, 64-bit only; line confidence, angle and symbol-level output are not returned on iOS [fetched] — [d-date/google-mlkit-swiftpm README](https://raw.githubusercontent.com/d-date/google-mlkit-swiftpm/main/README.md); [google_mlkit_text_recognition README](https://raw.githubusercontent.com/flutter-ml/google_ml_kit_flutter/master/packages/google_mlkit_text_recognition/README.md)
- Apple Vision customisation is limited to `recognitionLanguages`, `customWords` (ignored unless language correction is enabled, and unsupported for Chinese), `minimumTextHeight`, region of interest and recognition level [fetched] — [Recognizing Text in Images](https://developer.apple.com/documentation/vision/recognizing-text-in-images)
- Apple changed the `.accurate` models in iOS 27 without a new revision number, so apps cannot pin the earlier model ("there's no way to opt out") [fetched; developer report] — [Apple forum thread 851862](https://developer.apple.com/forums/thread/851862)
- Apple language gaps confirmed by Apple or sources citing Apple: Swedish was not supported in iOS 18 despite a WWDC24 claim [fetched]; Greek is not on the Live Text list [snippet] — [Apple forum thread 765905](https://developer.apple.com/forums/thread/765905); [textora.app](https://textora.app/blog/live-text-supported-languages/)
- `VNRecognizeTextRequest` is reported to miss vertical and stylized Chinese that Live Text reads, while Live Text's `ImageAnalysis` gives no bounding boxes [fetched; unanswered developer report, Aug 2026] — [Apple forum thread 842398](https://developer.apple.com/forums/thread/842398)
- Privacy statements: Apple, "all of Vision's processing happens on the user's device" [fetched]; Google AICore "doesn't store any record of the input data or the resulting outputs" and has no direct internet access [fetched]; Scanbot, "No data is transmitted to our or third-party servers" [fetched] — [Recognizing Text in Images](https://developer.apple.com/documentation/vision/recognizing-text-in-images); [Gemini Nano on Android](https://developer.android.com/ai/gemini-nano); [Scanbot Android example README](https://raw.githubusercontent.com/doo/scanbot-sdk-example-android/master/README.md)
- ML Kit GenAI APIs carry additional terms of service, and "Developers are solely responsible for the safety of their API client and their app's user experience" [fetched] — [Gemini Nano on Android](https://developer.android.com/ai/gemini-nano)
- Commercial SDK licence keys are bound to the app identifier (Microblink) and trial builds are time-limited (Scanbot: one minute per session without a licence) [fetched] — [BlinkID Android README](https://raw.githubusercontent.com/BlinkID/blinkid-android/master/README.md); [Scanbot Android example README](https://raw.githubusercontent.com/doo/scanbot-sdk-example-android/master/README.md)

### Inferences
- Bottom line for "smallest and fastest that still works well, including on old phones", from the evidence above:
  - **iPhone:** Apple Vision (`VNRecognizeTextRequest`) adds nothing to app size, works back to iOS 13, and its `.fast` level is the real-time option for old hardware. It scored best in the one independent accuracy comparison. Caveats are OS-dependent language coverage and the unresolved iOS 27 `.accurate` regression.
  - **Android with Google Play services:** ML Kit unbundled Latin is the smallest (about 260 KB) and runs from API 21; bundled (about 4 MB per script per ABI) is the choice when OCR must work offline on first launch.
  - **Android without Google Play services:** ML Kit bundled (unverified on such devices) or Huawei HMS ML Kit.
  - **Scripts outside the five ML Kit supports (Arabic, Cyrillic, Thai and others) on Android:** no platform-native option was found short of Gemini Nano on eligible flagships, so those cases fall to the open-source models covered by other researchers.
- Because both vendors can update models through the OS or Play services, on-device results are not reproducible across time the way a self-shipped model's are; teams that need stable behaviour should factor that in.

### Gaps
- ML Kit's terms of service and data-collection disclosures were not read (blocked host), so no statement on telemetry or usage restrictions is included; ML Kit's "free" status rests on a third-party review title.
- Whether ML Kit's bundled variant initialises on devices without Google Play services was not verified.
- No information was gathered on export restrictions, regional availability or enterprise licensing terms for any SDK.
